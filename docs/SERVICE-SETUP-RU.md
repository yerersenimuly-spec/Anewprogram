# Как подключить и развернуть Line

**Коротко:** приложению нужны ваш домен, публичный VPS и отдельно работающие API и LiveKit. В репозитории есть шаблоны и инструкции, но настоящий сервер здесь не развёрнут; покупка домена или VPS не выполнялась. Это руководство не заменяет проверку звонков с реальных телефонов и сетей.

## Что потребуется

1. **Домен, который принадлежит вам.** Купить его можно у любого регистратора; например, в [Cloudflare Registrar](https://www.cloudflare.com/products/registrar/) или [Namecheap](https://www.namecheap.com/domains/). Проверьте цену продления и доступность доменной зоны до оплаты. Доступы от аккаунтов регистратора и облака не передавайте в чат.
2. **VPS с Ubuntu 24.04 LTS и публичным IPv4.** Для первого небольшого испытания разумная отправная точка — 2 vCPU и 4 GiB RAM. Это не гарантия производительности и не результат нагрузочного теста. Серверная логика допускает группы до 8 участников, но это не означает, что один VPS выдержит восемь одновременных звонящих на максимальном битрейте. Учитывайте исходящий трафик/его цену, резервные копии и регион поближе к пользователям.
3. **SSH-ключ.** Создайте ключ на своём компьютере (`ssh-keygen -t ed25519`) и добавьте в панель VPS только публичный файл `.pub`. Оставьте вход по SSH-ключу, ограничьте SSH своим IP, включите двухфакторную защиту аккаунта и проверьте сумму/условия тарифа перед созданием сервера.

Примеры VPS — [Hetzner Cloud](https://console.hetzner.cloud/) и [DigitalOcean Droplets](https://cloud.digitalocean.com/). В панели выберите Ubuntu 24.04, близкий к пользователям регион, размер выше и публичный IPv4. У разных регионов, планов, IPv4 и исходящего трафика разные условия: актуальную стоимость проверяйте в панели перед подтверждением. Официальные инструкции по созданию: [Hetzner](https://docs.hetzner.com/cloud/servers/getting-started/creating-a-server/) и [DigitalOcean](https://docs.digitalocean.com/products/droplets/how-to/create/).

## DNS и сетевой доступ

Для домена `example.org` заведите DNS-записи `A` для `api.example.org`, `rtc.example.org` и `turn.example.org` на публичный IPv4 сервера. Если у VPS есть настроенный и доступный пользователям IPv6, отдельно проверьте его перед добавлением `AAAA`; ошибочный `AAAA` может увести часть телефонов на неработающий адрес. При DNS у Cloudflare установите для этих записей **DNS only** (серое облако), а не HTTP-прокси: WebRTC/TURN используют UDP и прямую сетевую связность. DNS-only показывает IP сервера, поэтому firewall обязателен. Справка Cloudflare: [статус прокси](https://developers.cloudflare.com/dns/proxy-status/).

Настройте входящие правила **и в облачном firewall, и в UFW на Ubuntu**, если он используется:

| Порт/протокол | Для чего | Доступ снаружи |
| --- | --- | --- |
| `80/tcp`, `443/tcp` | получение/обновление TLS и публичные API/LiveKit WebSocket через TLS proxy | да |
| `7881/tcp` | ICE/TCP для LiveKit | да |
| `50000–60000/udp` | основной ICE/WebRTC media диапазон по текущему шаблону | да |
| `3478/udp` | встроенный LiveKit TURN/UDP | да |
| `5349/tcp` | TURN/TLS в текущем `deploy/livekit.yaml` | только с оговоркой ниже |
| `3000/tcp`, `7880/tcp` | внутренние порты API и LiveKit за reverse proxy | **не** открывать публично |

В шаблоне TURN/TLS использует `5349/tcp`, но официальное руководство LiveKit говорит: без layer-4 load balancer TURN/TLS должен объявляться на `443/tcp`. Здесь `443/tcp` уже нужен Caddy для `api`/`rtc`, поэтому одной замены числа в firewall недостаточно: потребуется отдельный публичный IP для TURN или TCP-pass-through/L4 балансировщик. Для сетей с жёсткими firewall-правилами предпочтительнее [официальное развертывание LiveKit на VM с генератором конфигурации](https://docs.livekit.io/transport/self-hosting/vm/): оно рассчитано на Caddy и TURN/TLS на 443. Эта схема Docker/Caddy не является готовой интеграцией API Line: не запускайте второй Caddy на тех же `80/443`; добавьте API-маршрут в прокси LiveKit либо разместите API за отдельным публичным адресом. Порты и пояснения LiveKit: [firewall reference](https://docs.livekit.io/transport/self-hosting/ports-firewall/).

## Развертывание репозитория

Шаблоны проекта рассчитаны на **один Node-процесс и native LiveKit Server**, без Docker для этой схемы. Для быстрого теста можно следовать [`deploy/README.md`](../deploy/README.md) и [`server/README.md`](../server/README.md), понимая ограничение TURN/TLS выше. Для широкой доступности звонков сначала решите вопрос TURN/TLS: не обещайте, что звонки пройдут через любую корпоративную сеть только потому, что `mediaReady` включён.

1. Войдите по SSH обычным пользователем с `sudo`. Обновите Ubuntu. Установите Git и **Node.js 24**. Например, официальный скрипт NodeSource для Ubuntu/Debian 24.x добавляет пакетный репозиторий, затем установите пакет и проверьте версию:

   ```sh
   curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
   sudo apt-get install -y nodejs git
   node --version   # должно быть v24.x
   npm --version
   ```

   Установщик добавляет внешний APT-источник; если не хотите его использовать, выберите Node 24 другим способом и настройте systemd так, чтобы он видел этот `node`. В проекте требуется Node `>=24` (`server/package.json`).

2. Скопируйте/получите **разрешённую вам приватную** копию проекта на VPS. Не делайте репозиторий публичным только ради развёртывания и не вставляйте access token в URL Git. Установите зависимости и прогоните серверные проверки:

   ```sh
   cd /путь/к/проекту/server
   npm ci
   npm test
   ```

3. Сгенерируйте независимые случайные `LIVEKIT_API_KEY` и `LIVEKIT_API_SECRET`. Создайте `/etc/livekit/api-keys.yaml` как YAML-мапу `ключ: секрет`, совпадающую с этими значениями, владельцем LiveKit-процесса; права файла — `0600`. Перенесите [`deploy/livekit.yaml`](../deploy/livekit.yaml) в `/etc/livekit/livekit.yaml`, замените `turn.example.org`, DNS-имена и пути сертификатов. Шаблон проверялся с LiveKit Server **1.13.7**; закрепите эту версию из [официальных релизов](https://github.com/livekit/livekit/releases) и отдельно проверяйте обновления. TURN-сертификат для `turn.<ваш-домен>` должен быть доверенным, доступным LiveKit и автоматически обновляться; приватный ключ не помещайте в Git.

4. Поставьте Caddy из [официальной инструкции установки для Ubuntu](https://caddyserver.com/docs/install) и используйте [`deploy/Caddyfile`](../deploy/Caddyfile), заменив `example.org` на свой домен. В нём API проксируется на `127.0.0.1:3000`, а LiveKit WebSocket — на `127.0.0.1:7880`; Caddy выдаёт сертификаты для этих имён после того, как DNS указывает на сервер и доступны `80/443`.

5. Запустите API как отдельный systemd-сервис от непривилегированного пользователя. В защищённом `/etc/line/api.env` задайте:

   ```text
   HOST=127.0.0.1
   PORT=3000
   DATA_FILE=/var/lib/line/identities.json
   ADMIN_DATA_FILE=/var/lib/line/admin.json
   LIVEKIT_URL=wss://rtc.<ваш-домен>
   LIVEKIT_API_KEY=<тот же ключ из api-keys.yaml>
   LIVEKIT_API_SECRET=<тот же секрет из api-keys.yaml>
   ADMIN_PASSWORD_HASH=<scrypt-хеш, создаваемый ниже>
   ```

   Это **имена и примеры значений, не готовые секреты**. Создайте `/var/lib/line` с правом записи для пользователя API, а env-файл — без доступа для других (`root`, режим `0600`). Не кладите секреты в репозиторий, Android APK, shell-команду или чат. В systemd задайте `WorkingDirectory=<путь>/server`, `ExecStart=/usr/bin/node <путь>/server/src/index.js`, `EnvironmentFile=/etc/line/api.env`, `User=<не-root-пользователь>`, `Restart=on-failure`; после этого выполните `systemctl daemon-reload`, включите сервис и проверьте `systemctl status`/`journalctl -u <имя-сервиса>`. Для Caddy и LiveKit также настройте автозапуск и перезапуск при отказе.

6. Проверьте `https://api.<домен>/health`: ответ должен быть `{"status":"ok"}`. Затем проверьте API, TLS и звонки с реального телефона и другой сети. Это отдельные проверки: `mediaReady` показывает только корректную конфигурацию LiveKit, а не доступность UDP/TURN.

### Код подключения и pins

В профиль телефона импортируется код вида `LINE1...`; адреса должны быть `wss://api.<домен>/signal` и `wss://rtc.<домен>`. Приложение проверяет отдельные SHA-256 SPKI pins для TLS-ключей API и LiveKit. Получите pin с сертификата, который вы доверенно установили на сервере, не копируйте его из случайного сообщения или недоверенного соединения:

```sh
openssl x509 -in <путь-к-сертификату-хоста.pem> -pubkey -noout \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -binary | openssl base64 -A
```

Добавьте к результату префикс `sha256/`; заведите проверенный запасной pin и план его ротации до смены ключа сертификата, иначе старые APK могут потерять доступ. Создать профильный код из доверенных адресов и pins можно имеющимся скриптом:

```sh
node scripts/connection-code.mjs \
  --api 'wss://api.<домен>/signal' --api-pin 'sha256/<pin>[,sha256/<резервный-pin>]' \
  --media 'wss://rtc.<домен>' --media-pin 'sha256/<pin>[,sha256/<резервный-pin>]'
```

Передайте полученный код владельцу телефона приватно. Не включайте в код серверные API-секреты LiveKit или пароль администратора: их там нет и быть не должно.

## Защищённый раздел администратора

Администратор — не фиксированный код в APK. Сначала подключите профиль к уже работающему API и зарегистрируйте установку; затем трижды нажмите вкладку «Профиль» в пределах примерно 1,8 секунды и введите серверный секрет. Сервер проверяет его по scrypt-хешу. Если `ADMIN_PASSWORD_HASH` отсутствует/неверен, вход выключен; обхода в приложении нет. Создайте секрет длиной **12–128 символов** на сервере:

```sh
cd /путь/к/проекту
node server/scripts/hash-admin-password.mjs
```

При вводе в интерактивном терминале символы скрыты; скопируйте выведенный `scrypt$...` хеш в защищённый `/etc/line/api.env` как `ADMIN_PASSWORD_HASH=...`, затем перезапустите API. Сохраните исходный секрет в своём менеджере паролей: восстановить его из хеша нельзя. Ввод секрета в приложении передаётся только через настроенное TLS/WSS-соединение. После пяти неверных попыток с одного адреса сервер блокирует новые попытки на минуту; успешная админ-сессия истекает не позднее чем через пять минут и закрывается при выходе/сворачивании приложения.

Настройки проверяются **сервером**, а не только скрыты в интерфейсе: админ может включать/выключать звонки и сообщения, приостанавливать регистрацию новых установок, задавать максимум участников звонка (2–8), блокировать/разблокировать известный восьмизначный номер и завершать активную группу. Изменение правил сохраняется в `ADMIN_DATA_FILE` и рассылается подключённым клиентам; отключение звонков завершает текущие звонки, блокировка отключает учётную запись. Выключение регистрации запрещает новые установки, но не удаляет существующие аккаунты. Панель показывает число подключённых/зарегистрированных установок, активные звонки и состояние конфигурации LiveKit, экспортирует диагностический отчёт без текста чата. Администратор также может изменить адреса/pins своего профиля, скопировать код подключения `LINE1` для пользователей и переподключить приложение.

Журнал администратора намеренно не пишет содержимое сообщений, аудио, ключи, IP или номера участников; в нём только фиксированные тип/результат события и время. Это **не долговременный аудит**: сохраняются только последние 100 событий в памяти текущего процесса, они исчезнут после перезапуска. Приватные Signal-ключи и plaintext чата остаются на телефонах, администратор не может прочитать текст через API. E2EE аудио настраивает Android-клиент: LiveKit-токен сам по себе его не включает. LiveKit/TURN и сервер всё равно видят сетевые метаданные (например, IP, участников и время); не включайте запись/egress или недоверенных ботов, если это противоречит вашей модели приватности. Настройки и список блокировок, напротив, хранятся в отдельном защищённом JSON-файле. API рассчитан на один экземпляр: не запускайте несколько копий с общими JSON-файлами. Делайте закрытые резервные копии `/var/lib/line` и периодически проверяйте восстановление.

## Что означает «удалить сообщение» и размер чата

Команда приложения **«Удалить на этом устройстве»** удаляет сообщение из локальной истории только на текущем телефоне; копия собеседника остаётся. Сервер временно пересылает шифротекст подключённому получателю и не держит offline-очередь, поэтому это не удалённый отзыв уже доставленного сообщения и не стирание копий собеседника.

Сообщения по-прежнему ограничены 24 KiB зашифрованного пакета (UI принимает текст до 2 000 символов). Фото, файлы и голосовые сообщения идут отдельным путём: клиент шифрует файл сам, а сервер временно хранит только шифртекст в `${DATA_FILE}.blobs/` (по умолчанию до 26 MiB на файл, 7 суток после загрузки, 1 GiB всего, 200 MiB на отправителя; пределы задают `BLOB_*`). Ключ и ссылка на файл передаются получателю внутри обычного зашифрованного сообщения. Получатель после сохранения подтверждает файл (`blob_ack`), и сервер его удаляет. Формат — в [`API.md`](API.md#37-вложения-v8). Размер APK выбирайте по целевым ABI и подписанному релизу, а не наращивайте пустыми данными.

## Push-уведомления и обновление до 0.8.0

**Push без Firebase.** Сообщения и звонки будят приложение через UnifiedPush: на телефоне нужен дистрибьютор (например, ntfy), а сервер отправляет ему подсказку «переподключись» без текста и номеров. Свой ntfy на том же VPS за Caddy, переменные, ограничения (остановленное приложение не разбудить) и диагностика — в [`PUSH-SETUP.md`](PUSH-SETUP.md). Переменные `FCM_PROJECT_ID` и `GOOGLE_APPLICATION_CREDENTIALS` сервер 0.8.0 игнорирует; оставьте их в `/etc/line/api.env` как есть.

**Новые необязательные переменные** (по умолчанию ничего задавать не нужно): `PROFILE_FILE`, `PUSH_ENDPOINT_FILE`, `MISSED_FILE`, `BLOB_DIR`, `BLOB_MAX_BYTES`, `BLOB_TTL_MS`, `BLOB_QUOTA_BYTES`, `BLOB_SENDER_PENDING_BYTES`, `CALL_RESUME_GRACE_MS`, `PUSH_ALLOW_PRIVATE_ENDPOINTS`, `APNS_KEY_FILE`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC`. Значения и смысл — в [`API.md`](API.md#7-переменные-окружения). Новые файлы появляются рядом с `DATA_FILE` только при первом использовании; убедитесь, что пользователь API может писать в этот каталог (при `ProtectSystem=strict` он должен быть в `ReadWritePaths`).

**Обновление действующего сервера не трогает данные и секреты.** Формат файлов личностей, администратора и почты не изменился, окружение остаётся прежним. Порядок: резервная копия каталога данных; новый код в отдельный каталог и `npm ci --omit=dev`; `node scripts/check-data-compat.mjs <копия DATA_FILE>` на **копии** данных (скрипт только читает; код возврата 0 — совместимо); остановка сервиса, замена каталога кода и запуск; проверка `/health` и входа с телефона. Откат — вернуть прежний каталог кода: данные менять не нужно, а устаревший `${DATA_FILE}.push.json` не изменялся, поэтому FCM у 0.7.1 снова заработает. Подробные команды — в [`API.md`](API.md#9-обновление-действующего-vps-без-потери-данных).
